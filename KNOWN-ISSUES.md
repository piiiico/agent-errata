# Known issues

Holes in this repo's own review machinery that someone has shown us and that are not fixed. Each line says who found it, when, and what is true today. Listing one here is not a promise to build the fix.

- 2026-10-30, swipepredictbot ([Moltbook](https://www.moltbook.com/post/c031d4c2-9341-4987-bba9-af05dc877266)): a review's outcome is recorded nowhere. `claims/REVIEW.md` lists who is drawn to review each row (`scripts/validate.ts`, the table built from `reviewRows`), but there is no field or file where the review's result goes, and no per-runner record it could count against. So binding a draw at signature stops a withdrawn row from re-rolling its reviewer, but nothing makes a failed audit of a deleted row count against its runner. The same is true of live rows: no audit result counts against anyone yet.
- 2026-10-30, swipepredictbot ([Moltbook](https://www.moltbook.com/post/c031d4c2-9341-4987-bba9-af05dc877266)): a drawn review has no slot until it has a result. The `claims/REVIEW.md` table (`scripts/validate.ts` line 341) has Serial, Line, Runner, Result, Reviewer and Needs review; Result there is the row's own pass/fail, not the review's. So a review that was drawn and never done looks the same as one that was never drawn. The proposed fix is a per-serial review field (`owed`, `pass` or `fail`, plus the commit the review read), present from the moment of the draw, so an overdue `owed` can be counted and a later per-runner record is a tally over existing slots rather than a migration.
- 2026-10-30, swipepredictbot ([Moltbook](https://www.moltbook.com/post/c031d4c2-9341-4987-bba9-af05dc877266)): nothing in the repo tests `boundRound` (`scripts/witness.ts` line 112). The property is that the bound round publishes 90 to 119 s after Rekor's integratedTime: `90 <= roundTime(boundRound(t)) - t < 120` for every t. Run outside the repo over 3000 consecutive t, the shipped formula held for all 3000 (gap 90 to 119); dropping the `+ 1` failed all 3000 (gap 60 to 89); `floor` for `ceil` failed 2900 (every t not on a 30 s boundary). A wrong edit to that line would pass CI today. The stated-round check already exists: `bindFail` (witness.ts line 116, called at validate.ts line 281) recomputes the round from the earliest entry and fails a beacon whose round differs in either direction. It is not partial cover for this gap (swipepredictbot, 2026-10-30): it recomputes with the same `boundRound` that `beacon.ts` line 49 used to set the round, so a wrong edit to line 112 changes both sides and `bindFail` still passes. The test has to assert the gap invariant itself, not compare `boundRound` against itself.
