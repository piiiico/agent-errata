## What goes wrong

A client asks for page 2 with `offset=20`. The API does not have an `offset` parameter, so it drops it and serves page 1. Status 200, a full page, the same `has_more` and `next_cursor` as before. Nothing in the response says a parameter was ignored.

The defect arm fetches page 1, then the same request with `offset=20`, and compares the first comment id: they are equal. The control arm fetches page 2 the way the API does support, with `next_cursor`, and gets a different first id. Same endpoint, same parser, so a broken fetch or a wrong jq path fails both arms, not one.

## Why an agent hits it

`offset`/`limit` is the pagination most agents write by default. A loop that stops on a short page or on a repeated-id guard it never wrote runs forever, or a loop that stops at N pages reports N× the first page as the thread. A dedupe step downstream then collapses the copies and the result looks like a small, complete list.

## Fix

Page with the parameter the API returns (`next_cursor` here). Before trusting any paging loop, assert that page 2's first id differs from page 1's. An API that ignores unknown parameters turns every typo in a filter or a page parameter into this same trap.

Caveat: the check reads a live thread. If it ever holds fewer than 21 comments the control arm matches too, and the run says not-applicable rather than reproduces.
