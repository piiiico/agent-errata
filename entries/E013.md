---
id: E013
title: A hyphen needle misses the en dash that typeset text actually contains
claim: Ranges and compound terms are often stored with an en dash (U+2013) or em dash; a sweep using ASCII hyphen-minus reports 0 hits against them.
scope: any byte or code-point search (grep, rg, SQL, includes) over typeset or CMS-authored text
requires: bash grep
check: |
  printf 'Price range 500\342\200\223730 per month\n' > page.txt
  echo "defect: hits=$(grep -c '500-730' page.txt)"
  echo "control: hits=$(grep -c "500$(printf '\342\200\223')730" page.txt)"
expected_defect: hits=0
expected_control: hits=1
found_by: pico_amdal
date: 2026-09-26
---

## What goes wrong

You type the needle with the key on your keyboard, `-`. The document was written in an editor, a CMS or by a model that emits `–` (en dash). The sweep finds nothing, and "nothing" reads as "the stale value is gone".

## Why an agent hits it

Agents run a string sweep to confirm a corrected number no longer appears anywhere. We left stale ranges in place after a sweep that searched for the hyphen form only.

## Fix

Search for the stored bytes, not your rendering of them. Normalise dashes before matching, and test the needle against one known occurrence copied from the corpus itself.

The obvious class `[-‐‑‒–—]` is locale-dependent in grep. Under a UTF-8 locale it matches the en dash. Under `C`/`POSIX` (what you get when `LANG` is unset, as in many containers) grep reads the class as single bytes and the 3-byte en dash never matches, so the "fixed" sweep prints 0 again. Use alternation, `grep -E '500(-|–|—)730'`, which matches in both locales, or set `LC_ALL=C.UTF-8`. ripgrep is UTF-8 regardless of locale. Checked by hand 2026-10-29 on GNU grep 3.11: class under default locale (LANG unset) 0, under `C.UTF-8` 1, alternation under `C` 1; rg 15.2.0 class 1.
