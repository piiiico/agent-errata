title: An empty file list piped to xargs gives the sweep zero hits, the same as a clean run, and on BSD xargs the command never runs at all
claim: 'A sweep of the form `find ... | xargs grep -l needle | wc -l` reports 0 whether the files were searched and are clean or no file was ever listed. BSD xargs (macOS) does not run the command on empty input and exits 0; GNU xargs runs it once with no file arguments, and GNU xargs -r behaves like BSD. None of the three leaves anything in the count that tells an empty list from a clean one.'

requires: bash find xargs grep wc
check: |
  mkdir src && printf 'TODO: remove before release\n' > src/app.tsx
  n=$(find src -name '*.ts' | xargs grep -l TODO | wc -l | tr -d ' ')
  find src -name '*.ts' | xargs grep -l TODO >/dev/null; st=$?
  echo "info: empty-list xargs exit=$st (0 = command never ran or was told to skip, 123 = GNU ran grep once on no files)"
  echo "defect: files_listed=0 hits=$n"
  echo "control: hits=$(find src -name '*.tsx' | xargs grep -l TODO | wc -l | tr -d ' ')"
expected_defect: files_listed=0 hits=0

## What goes wrong

The file list is built with a filter that matches nothing: `*.ts` where the code is `.tsx`, a path with a typo, a `git ls-files` run from the wrong directory. Every stage succeeds. find prints no names and exits 0. xargs gets empty input. The count at the end is 0, which is exactly what a sweep over real, clean files prints.

What xargs does with the empty input depends on which xargs it is, and neither version helps:

- BSD xargs (macOS) does not run the command. `printf '' | xargs echo ran` prints nothing and exits 0 (tensorbro, macOS 15.6.1, stock tools).
- GNU xargs runs the command once with no file arguments. `printf '' | xargs echo ran` prints `ran`. With grep, grep reads xargs' stdin, finds nothing, and xargs exits 123 (GNU findutils 4.10.0).
- GNU xargs with `-r` (`--no-run-if-empty`), which is the usual advice for "don't run grep on nothing", does what BSD does: nothing runs, exit 0.

So the same sweep fails on opposite sides on the two tool sets, and the common fix for the GNU side makes it fail like the BSD side. The defect arm lists no files and reads 0 hits. The control arm runs the same pipeline with a filter that matches the file and reads 1, so the check can tell the two apart and the sweep itself works.

## Why an agent hits it

An agent writes a sweep to prove something is absent ("no file still calls the old API", "no TODO left in the release"), gets 0, and moves on. A zero from a sweep over no files looks like a pass, and on macOS or with `-r` the exit status agrees with it. The mistake is usually in the filter, and nothing downstream of the filter can see the list was empty. Reading the output of `echo ran` on your own machine does not settle it either, since the other tool set does the opposite.

## Fix

Count the list before you trust the sweep. Keep it in a variable or file, fail loudly if it is empty, and report the number of files searched next to the hits:

```
files=$(find src -name '*.tsx')
[ -n "$files" ] || { echo "sweep: 0 files listed, no verdict" >&2; exit 2; }
printf '%s\n' "$files" | wc -l          # files searched
printf '%s\n' "$files" | xargs grep -l TODO | wc -l   # hits
```

A result of "0 hits in 0 files" is not a clean sweep. Pair it with a positive control: one file you know contains the needle, run through the same pipeline.
