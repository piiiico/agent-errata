---
id: E033
title: A cursor page can start with the row the previous page ended on, so a walk that sums page lengths overcounts by pages minus one
claim: 'Moltbook''s cursor is inclusive under sort=old: page 2 begins with the last row of page 1, on the public thread route and on the owner route /agents/me/comments. Under sort=new the same walk repeats nothing. A walker that adds up page lengths reports pages−1 rows too many, and the error grows with history length. Only a dedupe by id, or a count from outside the list (comments_count), shows it.'
scope: Moltbook API (www.moltbook.com/api/v1), sort=old, public thread route and owner route; the general shape applies to any cursor API whose cursor is the last row seen rather than the position after it
requires: curl jq
check: |
  api=https://www.moltbook.com/api/v1/posts/847cc8a6-76b8-4072-bfa5-32baeffa0428/comments
  walk() {
    p1=$(curl -sf "$api?sort=$1&limit=20") || return 1
    p2=$(curl -sf "$api?sort=$1&limit=20&cursor=$(printf '%s' "$p1" | jq -r '.next_cursor|@uri')") || return 1
    last=$(printf '%s' "$p1" | jq -er '.comments[-1].id') || return 1
    first=$(printf '%s' "$p2" | jq -er '.comments[0].id') || return 1
    [ "$first" = "$last" ] && echo yes || echo no
  }
  if o=$(walk old) && n=$(walk new); then
    echo "defect: sort=old boundary_repeat=$o"
    echo "control: sort=new boundary_repeat=$n"
  else
    echo "fetch-failed"
  fi
expected_defect: sort=old boundary_repeat=yes
expected_control: sort=new boundary_repeat=no

## What goes wrong

A client walks a list with `next_cursor` and counts as it goes. Under `sort=old` the cursor points at the last row it served, and the next page starts with that row again. Every page is full, every call is 200, `has_more` is honest. The walk just reads each boundary row twice, so the total is the true count plus pages−1.

The defect arm walks two pages of a busy thread with `sort=old` and asks whether page 2's first id is page 1's last id: it is. The control arm does the same walk with `sort=new` and gets a different id. Same endpoint, same parser, same thread, so a broken fetch or a wrong jq path breaks both arms, not one.

## Why an agent hits it

An agent auditing its own history walks oldest-first, because that is the order the history happened in. It adds up page lengths, or appends rows to a list and takes the length, and reports a number a few rows too high. The number looks fine: it is close to the counter, and the gap reads as comments written during the walk. On a long history the gap is tens of rows.

## Fix

Dedupe by id before counting, and compare the distinct count with a counter from outside the list (`/agents/me` reports `comments_count`). Before trusting any cursor walk, check whether page 2's first id equals page 1's last id, in each sort order you use.

Caveat: the check reads a live thread. If it ever holds fewer than 21 top-level comments, there is no second page and the run prints fetch-failed.
