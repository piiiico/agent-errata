title: A per-run dollar cap is checked after each model call returns, so the call that crosses it is billed in full and the cap is not a ceiling
claim: 'Claude Code stops a run once its own cost meter passes --max-budget-usd, but it reads the meter only after a call has come back. The call that crosses the cap is already paid for. With a 1 USD cap and calls priced at 3.015 USD, the run stops at 3.015 USD. The real ceiling of one run is the cap plus its most expensive single call, and a fleet of capped workers can spend the sum of the caps plus one call per worker.'

  # Stand-in for the Anthropic API on localhost: every call that offers tools gets a tool call back and reports
  # 1,000,000 input and 1,000 output tokens. Claude Code prices that with its own table. Nothing leaves the machine.
  cat > loop.ts <<'EOF'
  let n = 0;
  Bun.serve({ port: Number(process.env.PORT), hostname: "127.0.0.1", async fetch(req) {
    const j: any = await req.json().catch(() => ({}));
    const names: string[] = (j.tools || []).map((t: any) => t.name);
    const tool = names.includes("Read") ? "Read" : names[0];
    const content = tool ? [{ type: "tool_use", id: `toolu_${++n}`, name: tool, input: { file_path: `${process.cwd()}/a.txt` } }] : [{ type: "text", text: "OK" }];
    const usage = tool ? { input_tokens: 1000000, output_tokens: 1000 } : { input_tokens: 1, output_tokens: 1 };

  }});
  EOF
  echo hi > a.txt
  port=$((20000 + RANDOM % 20000))
  PORT=$port bun loop.ts >/dev/null 2>&1 & srv=$!
  sleep 1
  run() {
    HOME="$PWD/home-$1" CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1 ANTHROPIC_BASE_URL="http://127.0.0.1:$port" ANTHROPIC_API_KEY=sk-ant-local-fake \

## What goes wrong

A run gets a dollar cap: `claude -p ... --max-budget-usd 1`. The natural reading is "this run will not cost more than 1 USD". What the harness does is different. It sends a call, waits for the response, adds the usage the provider reports to its meter, and only then compares the meter with the cap. Nothing stops the call that pushes the total over. That call is billed in full, whatever it costs.

The check points Claude Code at a stand-in API on localhost. Every call that offers tools gets a tool call back, so the run keeps going, and reports 1,000,000 input and 1,000 output tokens. Claude Code prices each such call at 3.015 USD with its own table for `claude-sonnet-4-5`. With a 1 USD cap the run stops after one call, at 3.015 USD: three times the cap. The control runs the same server with no cap and `--max-turns 2`. It stops at 6.03 USD, which shows the meter reads the reported usage and that without a cap the loop simply continues.

Three more runs with a streaming stand-in, same prices: a 10 USD cap stopped after the fourth call at 12.06 USD (three calls were 9.045 USD, still under the cap, so a fourth went out). Same result on 2.1.287 (2 runs) and 2.1.289 (1 run). The cap stops the run. It does not bound the bill.

## Why an agent hits it

A cap flag looks like a ceiling, and the stop message ("Reached maximum budget ($1)") reads like one. Fleet tutorials add the caps up. AgentField's coding-agent fleet tutorial (2 October 2026, with Claude Code as the provider) says eight workers at $1.50 each "can never cost more than $12, no matter how badly one of them loops". That holds only if no single call can cost more than what is left under the cap. Claude Code's own flag does not work that way, and a long-context call can cost more than a worker's whole cap. One call at a large context costs dollars, not cents, and it is exactly the call a runaway loop makes. Claude Code's changelog also shows the cap has missed spend once before: "Fixed `--max-budget-usd` not stopping background subagents". Parallel subagents each have a call in flight, so the overshoot grows with the fan-out. This check does not measure that case.

The stand-in reports more input tokens than the request really holds, so the check cannot tell whether Claude Code would refuse a call whose real input alone was over the remaining budget. It shows only when the meter is read: after the call.

## Fix

- Budget for the cap plus one call. For a fleet: the sum of the caps plus, per worker, the largest call it can make (context window × input price, plus max output × output price), times the number of calls it can have in flight.
- If a ceiling must hold, put it where the money is: a provider-side hard limit on the API key or project, not a client-side flag the harness checks afterwards.
- A gateway or dispatcher that enforces caps can price the next call before sending it: input size is known, output is bounded by max tokens. Refuse the call if that bound does not fit what is left. Qwen Code's batch mode already refuses to submit when a plan sets `maxCostUsd` and the requests have no finite output bound to check it against.
