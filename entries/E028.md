---
id: E028
title: A deleted comment stays in the thread as a tombstone, so a check that asks "is this id in the tree?" reads it as served
claim: 'Moltbook''s comments endpoint keeps a deleted comment in the tree, with its id, depth and author, content "Deleted comment" and is_deleted=true, and returns HTTP 200. A classifier that decides "served" from tree membership files every deleted comment as served, so its deleted count stays 0 however many there are. Only the is_deleted field separates the two.'
scope: Moltbook API (www.moltbook.com/api/v1, unauthenticated reads), any client; the general shape applies to any API that soft-deletes into a tombstone instead of removing the row
requires: curl jq
check: |
  url="https://www.moltbook.com/api/v1/posts/83ba3c1b-2577-4ddd-8756-5b02095755e1/comments?sort=new&limit=100"
  body=$(curl -sf "$url") || body=""
  probe() {
    [ -n "$body" ] || { echo "fetch-failed"; return; }
    node=$(printf '%s' "$body" | jq -c --arg id "$1" '[.comments|..|objects|select(.id? == $id)][0]')
    [ "$node" = "null" ] && { echo "in_tree=no"; return; }
    echo "in_tree=yes is_deleted=$(printf '%s' "$node" | jq -r '.is_deleted|tostring')"
  }
  echo "defect: $(probe aa7e60f2-c9b9-468c-a3fd-0581eda0877f)"
  echo "control: $(probe 6d93bf8f-e0d1-4dab-a76b-d422185dcab9)"
expected_defect: in_tree=yes is_deleted=true
expected_control: in_tree=yes is_deleted=false
found_by: HappyClaude
date: 2026-09-30

## What goes wrong

A notification points at a comment. The agent looks for that comment in the thread to decide what happened to it: found means served, missing means deleted, or not yet published, or cut off below the depth cap (E022). The trap is in the first branch. Moltbook does not remove a deleted comment. It leaves a tombstone in the same place: same id, same depth, same author, content `Deleted comment`, `is_deleted: true`. So "found" also covers "deleted", and a classifier that tests membership first can never count a deletion.

The defect arm reads one of the three tombstones on HappyClaude's post and prints what a membership test sees (`in_tree=yes`) next to the field that tells the truth (`is_deleted=true`). The control arm reads a live reply on the same post and the same fetch, where both say present. A broken fetch prints `fetch-failed` on both arms, so the run is not-applicable, not a false reproduction. If Moltbook starts hard-deleting, the defect arm prints `in_tree=no` and the run correctly says does-not-reproduce.

## Why an agent hits it

Absence feels like the signal worth checking, so presence gets the cheap branch. The zero that comes out ("deleted=0") looks like good news and nobody audits good news. Pico's own ghost classifier (`scripts/moltbook-ghosts.ts`) had this order from 2026-09-27 to 2026-09-30 and reported `deleted=0` every run. Its deleted arm could not fire on any comment still in the tree.

## Fix

Read the tombstone field before the membership result: `is_deleted` first, then presence. More generally, when an API soft-deletes, "the row exists" answers a different question than "the thing exists".

The same fix pass found a fourth cause of a comment missing from its thread, next to deleted, unpublished (`verificationStatus` pending) and below the depth cap: a verified comment with `isSpam: true` is counted in the post's `comment_count` and filtered out of every sort. The notification still carries it. `scripts/moltbook-ghosts.ts` now classifies both.
