---
id: E036
title: In zsh, a bare $var followed by a colon and a modifier letter inside a string is a modifier, so "key:$x:tail" silently loses text
claim: zsh applies its modifiers (:h :t :r :e :a :A :P :l :u :q :Q :c, and :s with its two delimiters) to a bare $var, quoted or not. A key built as "prefix:$x:suffix" is rewritten with exit 0 when the suffix starts with one of those letters, and the letter is eaten even when the modifier changes nothing; ${x} braces stop it. bash, dash and sh do not do this, and neither does zsh when it emulates sh or ksh, so a line tested in bash breaks when the same agent runs it in native zsh.
scope: zsh in its native emulation (not when run as sh or ksh); not bash, dash or sh
requires: zsh
check: |
  zsh -c 'x=dir/name; echo "defect: key:$x:tail"'
  zsh -c 'x=dir/name; echo "control: key:${x}:tail"'
expected_defect: key:nameail
expected_control: key:dir/name:tail
found_by: DIADE
date: 2026-11-03
---

## What goes wrong

`"key:$x:tail"` is read by zsh as `$x` with the modifier `:t` (tail of a path) followed by the literal `ail`. The result is `key:nameail`, exit 0, no warning. With `:P` the value becomes an absolute path (`"name:$x:POST"` → `name:/abs/path/dir/nameOST`); with `:h` it becomes the directory. A modifier that changes nothing still eats its letter: `"svc:$x:rest"` → `svc:dir/name` followed by `est`. The worst case is `:s`, which takes the next character as a delimiter: `"label:$id:status"` with `id=abc` → `label:usbc` (it ran `s/a/us/`). `:s` rewrites silently only when its delimiter character comes back later in the word; when it does not (`:size`, `:src`, `:ssh`, `:sort`, or a bare `:s`) zsh stops with `bad substitution` and exit 1, and the rest of the command does not run. Every other letter in the list below is silent. The letters that fire are `a A c e h l P q Q r s t u` (plus `g`, `f`, `F`, `w`, `W` as prefixes to one of them); any other letter or a digit passes through unchanged, which is why the same habit works for weeks and then breaks on one key.

## Why an agent hits it

Agents build keys and paths in one-line commands, `name:$x:POST`, `label:$id:status`, `$host:user/file`, and test their habits in bash. On macOS the login shell has been zsh since 10.15 (Apple support, "Use zsh as the default shell on your Mac"), so a harness that gives the agent the user's shell gives it zsh. The finder hit it on 2026-10-31: a registry key built as `"name:$x:POST"` came out as `name:<absolute path>OST`, exit 0, and two lookups failed before anyone saw why, because nothing in the output said a modifier had fired.

## Fix

Brace every variable that is followed by a colon: `"${x}:tail"`. Test shell one-liners in the shell the harness will run them in, not in the one the author is used to.
