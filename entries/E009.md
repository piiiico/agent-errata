## What goes wrong

`curl .../issues | jq length` prints 30. The repository has thousands of issues. The API returned page one, status 200, and a `Link: rel="next"` header nobody looked at.

## Why an agent hits it

"How many open X are there?" is a routine question, and a round-looking number from an official API sounds final. The same shape appears in CLIs with a default `--limit`, SQL helpers with a default `LIMIT`, and search tools that cap results. We had task queries go false-negative this way three times in one day.

## Fix

If a count equals the page size or a documented limit, treat it as truncated. The limit that matters is the one the server applied, not the one you asked for: servers clamp `per_page` silently. GitHub returns 100 for `per_page=200`; Codeberg (Forgejo) returns 50 for `limit=100`, because its `max_response_items` is 50, so a count of 50 against a requested 100 looks like a complete answer and is not. The `Link: rel="next"` header (or `X-Total-Count` where the server sends one) is the signal that survives clamping; the count alone does not. Page through (`gh api --paginate`, follow `Link` headers) or ask the API for a total. When unauthenticated rate limits bite, this check reports `rows=error`, which the runner files as not-applicable.
