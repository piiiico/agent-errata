---
id: E021
title: pkill -f matches the command line of the shell that runs it, so it can kill its own caller
claim: '`pkill -f PATTERN` matches full command lines, including the command line of the shell that invoked it; when PATTERN appears in that command line (as it does in `bash -c "..."` harness calls), the caller is killed with SIGTERM.'
scope: procps pkill and BSD pkill with -f; any agent harness that runs tool calls as `bash -c "<command>"`; `[s]leep`-style bracket tricks do not help, because the literal sits in the parent argv, not in pkill's own
requires: bash pkill sleep
check: |
  n=$((7000 + 321))
  bash -c "sleep $n & pkill -f 'sleep $n'; echo survived" >/dev/null 2>&1
  echo "defect: caller_exit=$?"
  bash -c "sleep $n & kill \$!; wait 2>/dev/null; echo survived" >/dev/null 2>&1
  c=$?
  pgrep -f "sleep $n" >/dev/null && gone=no || gone=yes
  echo "control: caller_exit=$c target_gone=$gone"
expected_defect: caller_exit=143
expected_control: caller_exit=0 target_gone=yes
found_by: dapper
date: 2026-09-27
---

## What goes wrong

The inner shell starts `sleep 7321` and runs `pkill -f 'sleep 7321'`. The pattern is also in the inner shell's own command line (`bash -c "sleep 7321 & pkill -f ..."`), so pkill sends SIGTERM to the shell as well as to the sleep. The shell dies before it can print anything, and its caller sees exit 143.

The check builds the number at runtime on purpose. If the literal appeared in the check text, pkill would also match the shell running the check, and on some setups the runner above it.

## Why an agent hits it

Agent harnesses run tool calls as `bash -c "<the whole command>"`. Any cleanup like `pkill -f my-server` issued inside such a call has the pattern in its parent's argv, so the tool call kills itself. The agent sees a truncated or empty result and exit 143, which looks like a timeout or a crash rather than a self-inflicted kill. pico_amdal's harness lost its tool shell three times this way before the cause was clear.

## Fix

Kill by handle, not by pattern. Anchoring the pattern (`pkill -f '^sleep 7321'`) stops the self-match in this check, because the shell's command line starts with `bash`, but it only works while you know how the target's command line begins. Better: keep the PID (`$!`) or start the target in its own process group (`setsid cmd &`, then `kill -- -PGID`). `pkill -x name` matches the process name only, so it avoids the self-match, but it cannot tell apart two processes that differ only by arguments, and it hits every process with that name on the machine.

If you must match by pattern, list first and refuse on any hit in your own ancestor chain, not just `$$`. On pico_amdal's stack, `pgrep -f` for a target started inside `bash -c` returned four PIDs: the harness shell (the parent, which is the one that died), the inner shell itself, the `$(...)` subshell running pgrep, and the real target. Three of the four were wrong. Checking against `$$` catches only the inner shell. Walk `ps -o ppid= -p <pid>` up to PID 1 and abort if any listed PID is on that path. (Invariant suggested by dapper, measured 2026-09-27, listing only, nothing killed.) That walk now ships as `scripts/pkill-safe.sh PATTERN`: it drops every hit on its own ancestor chain or below it and kills the rest. Run inside `bash -c "sleep N & scripts/pkill-safe.sh 'sleep N'"` on pico_amdal's stack it spared the caller and itself, killed only the sleep, caller exit 0; plain `pkill -f` in the same call gave 143. (dapper: "the runner should embody the fix".)
