---
id: E030
title: A wrapper script with set -u but not set -e keeps going after a failed step and prints PASS with exit 0
claim: The option `set -u` only catches unset variables. Without `set -e` or an explicit check after each step, a failed verifier is followed by the wrapper's success lines, and the wrapper's own exit status is that of its last command.
scope: bash, zsh, dash, sh (any wrapper that runs steps in sequence without errexit)
requires: bash
check: |
  printf 'set -u\nfalse\necho PASS\n' > w.sh; out="$(bash w.sh)"; echo "defect: exit=$? out=[$out]"
  printf 'set -eu\nfalse\necho PASS\n' > c.sh; out="$(bash c.sh)"; echo "control: exit=$? out=[$out]"
expected_defect: exit=0 out=[PASS]
expected_control: exit=1 out=[]
found_by: imokokok
date: 2026-10-03
---

## What goes wrong

A run wrapper does `npm ci`, then a self-test, then `node verify.mjs`, then writes a status file and prints `PASS`. With only `set -u` at the top, a nonzero exit from any step is ignored: the next line runs, the status file gets `0`, and `PASS` is printed. The wrapper exits 0 because its last command succeeded. A failed verifier can also leave no new report while the wrapper claims success.

## Why an agent hits it

`set -u` looks like strict mode, so a reviewer who sees it at the top of a script assumes failures stop the run. Agents also read the wrapper's exit status or its last line instead of the verifier's own output. In both cases the failure never reaches the reader.

This case was reported in public by imokokok, in a static review of a pinned runner script on [aeoess/agent-governance-vocabulary#177](https://github.com/aeoess/agent-governance-vocabulary/issues/177#issuecomment-5948350976). The entry describes the failure mode in general, not that script.

## Fix

`set -euo pipefail` at the top. `set -e` does not fire inside `if`, `while`, `&&`/`||` lists or functions called from them, so for the steps that decide the verdict, check each one explicitly: `node verify.mjs || { status=$?; echo "FAIL $status" >&2; exit "$status"; }`. Write the status file from the verifier's actual status, never a literal `0`.

Then add the negative check imokokok asked for: in a fresh directory, force the verifier to fail after setup, and assert three things: nonzero exit, no report written, no `PASS` printed. A wrapper that has never been run with a failing verifier has not been tested on the case it exists for.
