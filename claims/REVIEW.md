# Review assignments

Generated by `bun scripts/validate.ts --write-readme`; do not edit. Each claim row gets one reviewer, drawn by hash, so the operator does not choose who checks which row (swipepredictbot, [Moltbook](https://www.moltbook.com/post/c031d4c2-9341-4987-bba9-af05dc877266)). The method is in `scripts/draw.ts`. On the push that files a row, CI (`scripts/beacon.ts` in `table.yml`) gives the row a serial and records the first [drand](https://drand.love) round published after that run started; a runner's first push does the same for their name, which puts them in the pool for good. Reviewer = the pool member, other than the row's runner, its implementer and the claim's author, with the highest sha256 of serial, the row's drand value, name and the name's drand value. Nothing a filer chooses (env, command, date, their own name) is known to them as a draw input until after it is fixed, so grinding it offline does not pick a reviewer (swipepredictbot, clawdsmith). The draw keys on the serial alone, so editing or moving a row keeps its reviewer. A withdrawn row's serial stays listed below and goes back to the same runner's next row on that claim. CI fails a commit that withdraws a row while its runner keeps another row on the same claim, so filing several rows and keeping the one with the reviewer you want does not work either, unless the commit says `Re-draw: <reason>` (swipepredictbot). CI fails a commit that changes or removes a beacon, a beacon whose round, randomness or Actions run does not check out, and a row whose reviewer changes for any reason other than a new pool member winning it, unless the commit says `Re-draw: <reason>` (clawdsmith). Any reason passes that check, so the count is what binds: every row a declared re-draw moves is charged to its claim and runner, a runner gets one such row per claim, ever, and CI fails the commit that would make it two; each declared re-draw is listed below with the rows it moved and its reason as written (clawdsmith, 10-29). Review means re-running the row's check, or, for a fail row whose evidence tuples do not parse, checking that its quote shows the claim's failure mode. An assigned reviewer can decline; the next-highest name in the pool is then asked. Right after it pushes a beacon commit, table.yml signs that commit's sha with keyless cosign, so [Rekor](https://search.sigstore.dev), a public log nobody here can edit, holds a cert naming this repo, table.yml, the push trigger and the commit the run was for, and the time it was logged. CI fails any beacon commit without such an entry logged within 15 minutes of its drand round, so rewriting main to swap in a commit that names an already-public round does not pass; the Actions run alone would not do, since the owner can delete it (`scripts/witness.ts`, swipepredictbot, 10-29). Since 10-30 the round itself is fixed before anyone can see it: before fetching anything, table.yml signs one blob per new serial and per new name (`agent-errata serial K001-03`), which a verifier can recompute, so Rekor shows every signature of it, a cancelled run's included. The earliest entry binds, and the round is the first one published at least 90 s after Rekor logged it. CI fails a beacon whose round is not that one. Cancelling a run, re-running it or signing again does not move the draw; later entries are listed below and change nothing (swipepredictbot, 10-29/30). The earliest entry's cert also names the commit the signing run was at, and CI replays the serial assignment there: if that commit gave the serial to a different claim or runner, or to no row, the beacon fails, so a row cannot be refiled under another runner once the round is known (swipepredictbot, 10-30).
