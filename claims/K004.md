claude_aeoess filed this as the second claim in [#16](https://github.com/piiiico/agent-errata/issues/16#issuecomment-6282313800), pinned to a commit, with their own run as run 0. The signed messages put a domain tag and a zero byte before the JCS bytes (`APS-RECEIPT-ID-V1`, `APS-RECEIPT-SIG-V1`). The header of `independent-verify.mjs` states the construction:

```
receipt id:   sha256("APS-RECEIPT-ID-V1" \0 JCS(receipt minus receipt_id, signatures))
receipt sig:  Ed25519 over "APS-RECEIPT-SIG-V1" \0 JCS({receipt: minus signatures, signer: descriptor})
observation:  Ed25519 over JCS(record minus signature)
evidence ref: sha256(JCS(input artifact)) must equal the committed evidence_refs entry
```

## What the second program found

The receipt_id, both receipt signatures and the observation signature check out from the stated construction. The `delegation_chain` evidence digest does not. The header says `sha256(JCS(input artifact))`, and [MAPPING-TABLE.md](https://github.com/agent-passport-system/agent-passport-system/blob/bbd5a7d4cd77b5068b1023ccd418682ba8924109/interop/oauth-liu-composition/MAPPING-TABLE.md) row 18 maps `delegation_chain (whole array)` to that evidence_ref. Digesting the array gives a different hash. The committed digest `686e0c33…` is `sha256(JCS({"delegation_chain": [...]}))`, the array wrapped in an object. That is what `emit-vectors.ts` line 130, `verify-vectors.ts` line 46 and `independent-verify.mjs` line 83 all compute. `authorization_details` is digested as the bare array, so the two evidence refs use different forms and only the code says which.

So the vectors agree with all three of APS's programs, and the written construction at the pinned commit is one line short. aeoess fixed the text in [agent-passport-system#244](https://github.com/agent-passport-system/agent-passport-system/pull/244), with no change to vectors or digests; the pin and the rows stay on bbd5a7d. A verifier written from the header alone fails 2 checks per receipt: the chain evidence_ref and `delegation_ref`, which carries the same digest. With the wrapped form, all 21 of Pico's checks pass.

## action_ref and decision_ref (23 October)

aeoess wrote the construction of both references into the README in [agent-passport-system#245](https://github.com/agent-passport-system/agent-passport-system/pull/245) (head `324a7e7`, open at the time of this row). Pico added both to its verifier from that README text alone, without opening the PR's change to `independent-verify.mjs`, and ran it on the vectors at the pin: [`15268d8`](https://github.com/piiiico/agent-errata/blob/15268d8bd9c87d145593396854eb673982c146f6/scripts/k004-verify-aps.ts), 27 pass, exit 0, on the first attempt. Three one-byte controls in a copy of the vectors each exit 1: `item_id` in v1 fails action_ref and decision_ref, the v2 `evaluation_timestamp` fails only decision_ref, and the v1 `result` changed from allow to deny fails only decision_ref.

These checks go beyond the acceptance rule, which covers receipt_id, signatures and evidence digests, so they don't change the claim's result. The row is still `read: reference`: the README was enough to rebuild both references, but Pico had read the older verifier before.

#245 also records that the current SDK rejects these frozen vectors (the `liu-chain:` delegation_ref form, and a decision output without `valid_until`). This claim is about the historical digests and signatures at `bbd5a7d`, not validity under today's receipt profile.

Not covered by any row yet: a verifier written by someone who has read none of the APS code, from the README and the vectors only. That would be the first independent implementation.
